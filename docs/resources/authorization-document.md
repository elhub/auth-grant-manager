# AuthorizationDocument

An authorization document records a proposed permission, its generated PDF,
and the result of successful signature verification.
Its API resource type is `AuthorizationDocument`.

## Identifier

The business identifier of the document is `id`, a UUID generated by Elhub.

* [Document process](../processes/authorization-document.md)

## Attributes

| Name | Description | Format |
|------|-------------|--------|
| `documentType` | Determines the purpose of the document and which grants confirmation creates. | Enum; see [v1 authorization types](../concepts/authorization-types.md). |
| `status` | Current state of the document. | Enum: `Pending`, `Approved`, `Expired`. |
| `requestedScopes` | Permission sought, including any limits on resources or changes. | Array of [requested scopes](../concepts/authorization-scopes.md). |
| `requestedGrantValidFrom` | Requested start of the resulting grant. | Optional date-time with offset; framework agreements only. |
| `requestedGrantValidTo` | Requested exclusive end of the resulting grant. | Optional date-time with offset; framework agreements only. |
| `externalReference` | Reference supplied by the caller and returned unchanged. | Optional string. |
| `validFrom` | When the document becomes open for confirmation. | Date-time with offset. |
| `validTo` | Deadline before which the document must be confirmed. | Date-time with offset; exclusive. |
| `createdAt` | When Elhub created the document. | Date-time with offset. |
| `updatedAt` | When Elhub last updated the document. | Date-time with offset. |

The PDF is available separately via the `file` link. Elhub generates and signs
it in the language supplied at creation. Successful confirmation replaces
the stored PDF with the returned signed file.

## Relationships

| Name | Description | Format |
|------|-------------|--------|
| `requestedBy` | Market entity asking for permission. | Market entity reference. |
| `requestedPrincipal` | Agent whose authority the requester seeks to exercise. | Agent reference. |
| `requestedOf` | Agent asked to provide authorization for the principal. | Agent reference. |
| `approvedBy` | Person whose signature confirmed the document. | Person reference; present on approval. |
| `authorizationGrants` | Grants issued on successful confirmation. | Array of [grant](authorization-grant.md) references when present. |

## Status transitions

| From | To | Cause |
|------|----|-------|
| New proposal | `Pending` | Successful generation, Elhub signing, and storage. |
| `Pending` | `Approved` | Successful confirmation before the deadline; signed evidence and grants are committed atomically. |
| `Pending` | `Expired` | Deadline reached without successful confirmation. |

`Approved` and `Expired` are terminal. There is no `Rejected` status.
Signature-validation failure does not create a new terminal state.

## Validation Rules

| Rule key | Rule | Status |
|----------|------|--------|
| AD-VAL001 | The authorization type determines which scopes, constraints, and grant dates may be supplied. See [v1 authorization types](../concepts/authorization-types.md). | DONE |
| AD-VAL002 | For supported v1 types, `requestedPrincipal` and `requestedOf` must resolve to organizations. | DONE |
| AD-VAL003 | The signed upload must be a nonempty `application/pdf` file of at most 1 MiB. | DONE |
| AD-VAL004 | The uploaded PDF must match the original Elhub-signed document, pass signature verification, and identify a resolvable signatory. | DONE |
| AD-VAL005 | Confirmation must be recorded before the deadline while the document is still `Pending`. | DONE |
| AD-VAL006 | If a grant end was requested, confirmation fails unless it is still after both the confirmation time and the grant's effective start. | DONE |

## Authorization

### Resource Level Authorization

The default policy is **deny**. The following policies apply to `AuthorizationDocument`.

| Policy key | Actor | Policy | Status |
|------------|-------|--------|--------|
| AD-001 | Market Entity | Create a document as `requestedBy` for a supported type when the Policy Decision Point confirms that `requestedOf` can represent `requestedPrincipal`. | DONE |
| AD-002 | Market Entity | Read, list, and retrieve PDFs for documents where it is `requestedBy`. | DONE |
| AD-003 | Organization | Read, list, and retrieve PDFs for documents where it is `requestedPrincipal`. | DONE |
| AD-004 | Market Entity | Submit a signed PDF for a document where it is `requestedBy`. The Policy Decision Point must authorize the signatory for `requestedOf` and `requestedPrincipal`. | DONE |

Anonymous callers have no policies. Being the signatory or `requestedOf` does
not by itself grant read access. There is no rejection, deletion, or editing
of the proposal.

### Attribute Level Authorization

There are no attribute-level policies for `AuthorizationDocument`.
